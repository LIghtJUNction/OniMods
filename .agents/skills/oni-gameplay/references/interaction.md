# 少往返交互与并行探索

本文件供实际控制游戏时首次读取。日常游玩复用这里的接口知识；当前存档的地图、库存、工单和风险仍按实际变化刷新。维护技能不代表获准启动游戏。

## 把探索移出关键路径

| 信息 | 什么时候读 | 什么时候重读 |
| --- | --- | --- |
| 主技能、编辑协议 | 会话首次需要时，选一种语言 | 文件发生变化或遇到协议错误 |
| `tools/list`、已用动作 schema | 首次连接；只查未知动作 | 重连、协议/Mod 变化或 schema 错误 |
| 建筑定义、字形、机制参考 | 当前目标第一次涉及时，批量查未知项 | 对应版本、DLC 或元数据变化 |
| 地图、库存、复制人、工单 | 暂停后读取影响本轮决策的部分 | 时间推进、相关写入、加载或世界切换 |

会话内保留已确认的工具、字形、建筑 ID、当前目标、等待句柄和最后停止原因。后续调用直接复用；不要每轮输出这份记录、重扫目录、重读攻略或反编译游戏。静态查询结果可复用，旧存档快照只能作为历史线索。

## 一次下达有用工作

- 常规任务先用一个最小状态结果和目标局部地图；目标已明确时不另做全基地侦察。
- 把同一局部范围的挖掘、地板或梯子合并成有界编辑；先看支撑、路线和液体，再提交。材料与可达性优先看同一预检返回的诊断，避免为每个格子重复查询。
- 参数已知且相互独立的调用放进 `call_many`，使用 `requireAllValid=true stopOnError=true`；通常取 `responseMode=summary`。需要句柄或完整子结果时取 `full`，不从截断摘要猜值。所有子调用也填写 `task`。
- 依赖上一步结果的调用在客户端顺序执行，读懂前一步结果再继续。`call_many` 没有结果变量、跨步骤事务或依赖编排能力。
- 自动挖后建返回句柄后，由已有流程推进到建成；不再逐格交替发挖掘、观察、建造。遇到阻碍才查该句柄和目标任务。

## 游戏运行时做什么

在有可执行工单、风险已核实且用户授权推进时，用有限的 `step_until` 保护运行窗口。一个控制者负责游戏；只读助手可同时查机制、建筑定义、攻略和已捕获快照，返回结论、出处与尚待核实条件。助手不恢复/暂停游戏，不提交工单，也不把旧地图当作最新状态。

优先选以下第一种执行方式：

1. **原请求等待完成**：直接调用 `step_until wait=true`。服务端在完成或停止后返回原请求，省去状态查询。先启动只读助手，或用宿主的挂起执行能力，让静态研究与这个请求同时进行。完成后只读缺少的目标状态。
2. **确实需要立即拿回控制**：使用 `wait=false`，保存返回的 `requestId`，去完成独立研究。需要结果时按该 ID 查询 `step_status`；仍在运行则交给宿主有界等待，避免高频轮询。没有完成推送，也没有自动唤醒 agent 的承诺。取消只针对该句柄。

先确认宿主是否支持子 agent 或挂起执行。有这些能力才安排并行研究；都不支持时用 `wait=true` 减少往返，研究在暂停后进行，并如实说明执行方式。

`step_until wait=true` 不能放进 `call_many` 充当可靠等待：批次不会等待子结果的 deferred 生命周期。客户端可在一次执行中顺序完成“提交已预检动作 → 检查回包 → 直接等待”，不必让 agent 为每个固定步骤重新推理；依赖结果不明时仍先处理错误。

示例：已准备好工作后，在工单终止、工作时有人空闲或打印舱就绪时暂停。按任务调整条件和时间，不把这个组合视为所有任务的默认策略：

```json
{
  "task": "推进现有工作，出现空闲或打印舱机会时暂停",
  "domain": "speed",
  "action": "step_until",
  "wait": true,
  "speed": 3,
  "maxGameSeconds": 60,
  "maxWallSeconds": 15,
  "until": {
    "any": [
      {"fact": "orders_complete"},
      {"fact": "dupes_idle", "quantifier": "any", "schedule": "work", "stableSeconds": 2},
      {"fact": "printing_pod_ready"}
    ]
  }
}
```

这是 `game_control` 的参数。两个时间上限都要显式设置；条件命中不影响严重威胁触发暂停。打印舱已经就绪会立即命中，先在暂停中处理物品或明确延后，不自动加人。工作空闲也可能是无路、缺料或资格问题，不能只继续扩大挖掘。夜间按日程休息不是工作空闲。

## 停止后只处理变化

先读取完成回包中的 `stopReason`、暂停状态、警报、工单状态及打印舱就绪信息。新鲜完成回包已确认暂停时，无需再发一个重复的暂停调用。缓存结果带有历史标记和年龄，不能当作刚完成的窗口。

- **正常进展/时间上限**：若没有新风险，定点确认目标后继续已有授权；不重新发现整个工具集。
- **工作时空闲**：查对应任务的材料、工作位置和候选快照，修复原因。可用时使用 `orders_control domain=task action=diagnose`；其排名属于各小人的缓存观察，不是权威实时全局队列。
- **暂停很快返回**：先看具体停止原因。既有 `alert` 也可立即命中，不能据此诊断暂停计数器故障。
- **失败/取消/零剩余**：核实目标建筑或地块。工单不再待办不等于目标完成。

暂停后把研究结论应用到当前局部快照，再提交下一批动作。只汇报完成、实际阻碍或重要事件，省掉“正在找工具/正在读文档”的逐步叙述。条件与状态字段的细节按需查[等待语义](../../../../docs/composable-game-waits.md)和[任务反馈](../../../../docs/gameplay-task-feedback.md)。
