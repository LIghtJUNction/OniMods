## 2. CycleTrim：先减少每帧需要做的事

### 2.1 液体候选扫描

候选扫描的工作是找出后续液体计算需要处理的格子。并行化有固定成本：分配任务、唤醒线程、汇总结果。如果输入很小，这些成本可能大于扫描本身；如果输入很大，零散访问和反复分配结果容器又会拖慢处理。

本轮按规模选择串行或连续分块扫描，复用结果缓冲区，并保持稳定的行优先顺序。这样既降低小输入的调度成本，也改善大输入的连续访问。没有通过改变选中格子或改变计算顺序来取得速度。

在 16 个固定场景的局部基准中，优化版候选扫描的中位加速比为 **1.155–6.835 倍**。测量使用 i9-12900HX、24 个逻辑处理器、Release/thin LTO/codegen-units=1；每个实现、每个场景预热 12 次，随后按 6 轮交替 ABBA/BAAB 顺序运行；每个实现每场景有 12 个计时批次，每批 200 次扫描。总计 384 个计时批次、76,800 次计时扫描，预热另计。基准最多使用 16 个工作线程，游戏配置使用 8 个，二者必须区分。

下表给出每种网格规模的 dense 场景绝对耗时，便于看清倍数对应的实际工作量。完整记录包含四种场景，而非仅下表四行。

| --- | ---: | ---: | ---: |
| 32 × 32 | 34.416 μs | 5.036 μs | 6.835× |
| 64 × 64 | 48.178 μs | 23.127 μs | 2.083× |
| 256 × 256 | 156.072 μs | 130.912 μs | 1.192× |

[完整基准数据与复现命令](https://github.com/LIghtJUNction/OniMods/blob/14dba75a5752c3142039a8660ce37cdf57d7082a/docs/cycletrim-liquid-candidates-20261120.json)。

**这个区间是候选扫描的耗时变化，不是游戏 FPS 的提升区间。** 一帧还包括模拟、主线程逻辑、渲染、同步和等待。只有位于当前关键路径上的耗时下降，才会反映到整帧时间。

### 2.2 温度预扫描的保守提前退出

先利用裁剪后区域面积计算上界；如果这个上界已经证明后续条件不可能满足，就省去整个网格的预扫描。符合条件的工作仍走原有计算路径，数值计算、选取顺序与工作集合不变。这类优化的收益取决于实际场景是否触发提前退出，不能用不相关的小存档推断大地图的收益。

### 2.3 去掉未使用的常驻初始化

删除未使用的 `ResidentCells` 与 `GpuPathfinder` 启动分配，保留公开 FFI 路径所需的延迟初始化。以 225,828 个填充后格子计算，减少了约 **17.229 MiB 的请求容量**及 3 个管线初始化。这是按分配尺寸计算的容量，不是显卡监控测得的 VRAM 下降。

4 个新增区域/暂存状态回归、1 个既有 CPU/GPU 热传导等价用例，以及 7 项真实 RTX GPU 测试通过。CPU CI 中另有 30 项依赖硬件的测试明确列为排除项，没有把它们记为软件回退测试通过。

### 2.4 多组分状态、液体填充与存档

液体格子有质量不代表任意派生字段都已经计算完成。原先“缺少数据时给出 0”容易让调用方把未知值误认为空格或零压力。本轮让 provider 同时发布值与可用性：液体体积分数采用已发布的归一化体积；未知压力返回不可用标记、空值及原因；填充不可用时通风口保持原逻辑。ABI 的 20/24/40 字节契约保持不变。

已有真实 Linux U60 验收使用游戏 763796、Unity 6000.3.17f1、3 名复制人的小存档，在有界运行后检查 6 个自然氧气/二氧化碳混合格子。保存、重新加载后的组分质量、温度与总质量按 binary32 精确一致；随后继续推进 4 个游戏秒。真实游戏覆盖了 2 种组分，22 种组分的覆盖来自宿主 FFI 测试，不能互相替代。

单一正质量组分继续保持 SIMSAVE v15 的字节兼容；具有第二种正质量组分时使用带 CRC 和严格原子校验的 ONIMIX `0x4f4d0001` 扩展。旧读取器返回状态 2 且不修改现有状态。**混合组分存档不能宣称与原版读取器兼容。** 元数据与实际 Unity Mono 的 inventory 差异为：16 个原生导入方法和 2 个回调委托的返回槽分别表示为 None/Retval，以及 3 个结构的默认对齐分别表示为 Pack=0/8。仅对这些等价表示作规范化，原 ABI 摘要常量不变，其他布局、方向和 marshaling 属性仍严格验证。Windows/macOS 原生 profile 仍限 U59/744825，没有对应 U60 真实游戏验收。

原始公开证据见仓库内 `docs/cycletrim-u60-multicomponent-live-20261120.json`。本轮派生字段补充有 25 项 native 发布测试及 CycleTrim 的 85 项相关检查；最终候选自然液体正填充的实机检查状态在第 7 节单独列出。

### 2.5 为什么没有直接宣称“帧率大幅提高”

曾在暂停状态对 JobManager.SimDebugView 分组取 28 帧样本，self 时间平均约 13.823 ms（3,870,394 ticks ÷ 10,000,000 ÷ 28）。这是分组归因，不能直接称为 16 个 PropertyTexture 行任务的独立耗时，也不能全算成 GPU 等待。约 0.854 MiB 的 RGBA 上传又在这个范围之外，各项不能随意相加。曾考虑在 Count==1 时绕过 JobManager，直接调用 DebugRunSingleThreaded，但这会改变异常处理语义，因此没有采用。

拟运行的整机 A–B–A 使用对称构建的 native 库、相同托管模组与存档、逐腿新进程，以及固定相机和速度。它仅比较 9c9c65e 到 bc156bf 的两项 native 增量：温度预扫描提前退出与未使用 GPU 初始化清理；A 基线已经包含此前的候选扫描优化。旧版 A 与新版 B 的首次构建曾因为归档时间戳导致 B 复用 A 产物；该 B 明确作废，重新实际编译后才得到不同哈希的有效 B。不能用这个无效产物作性能结论。

本轮整机 A–B–A 因实际资源压力未运行，第 7 节记录了验收边界。已准备的方案拟记录 Unity `Game.Update` 更新频率与零散的 GPU profiler LastValue；这些是计划采集的指标，并非本轮已取得的对照结果。方案没有物理呈现时间，不能称作屏幕实际呈现 FPS。分析不会平均各窗口的 p95，也不会将暂停画面当作模拟性能证据。

## 3. OniMcp 与 OniHarness：让调用结果和下一步操作可信

### 3.1 请求、取消与主线程边界

OniMcp 将能够在 HTTP 入口完成的请求校验移到主线程队列之前，避免无效请求先占队列再等待失败。任务查询与取消走独立路径。服务端在执行前确认取消的排队任务，不会在游戏恢复后继续执行；已经开始的操作仍可能完成。客户端超时本身不等于服务端已经取消。

基线验证包含 23 项 HTTP 检查和 19 组 Accept 协商检查，使用生产 HTTPListener 与调度器边界；游戏侧采用宿主桩，这两类宿主检查不等同于真实游戏覆盖。旧版的一个错误请求在约 3 秒处超时，负例验收在该处终止，没有把未继续执行的旧例算作完成。

Jlib 的主线程队列采用每帧最多 128 个回调、回调之间检查 4 ms 预算，并保留队列内 FIFO、既有 deferred 语义与生命周期取消。单个回调自身仍可能超过预算，这个设计不能抢占正在执行的用户代码。多组分读取链路另采用每线程 128 格批次缓存并按帧失效，provider/native 发布快照用原子版本号与短时读写锁，减少读取者长期占锁。

### 3.2 公开工具指导与坐标截图

当前工具目录有 7 个公开工具。本轮修复了已发现的错误返回指导，使相应下一步操作指向真实可调用的公共入口并包含必需参数；长结果提供 JSON 预览及通过 world_editor 固定 VFS 路径继续读取的指导。`launch.nextRead`、`parse_plan` 的 anchorSearch，以及坐标截图后的读取示例都补齐了公开 `world_editor` / `navigation_control` 路径。

搜索接受 `cell` 的兼容别名，并规范为 `cells`；世界 ID、任务说明、切换世界、聚焦格子及语义 ID 回退有明确提示。坐标轴标签限制在视口内 4 像素的安全边距，超出画面的轴标签不再硬画到屏外；请求矩形和相机范围保持原语义。

3 组新增回归在旧代码上失败、修复后通过。最终真人可读的数字标签与按图选格验证仍必须通过实际截图确认，不能以“截图成功排队”代替视觉验收。

U60 日报的真实读取覆盖 22 个条目、35 个名称，没有 MISSING；数据中有 14 条正向备注、17 条负向备注；另有宿主日志中明确记录的 66 个兼容适配断言，备注计数不属于测试用例数。发布门禁暴露的 IDE0005 已在 8 个文件中清理 9 个无用 using；专项快照（根提交 f0819fa、Jlib ee2670a 与八文件 using 补丁）的 Release 复验无警告、无错误，同一专项的分析器检查 448 个文件后无待应用修改。历史冷依赖及 Debug 构建警告仍保留；这不代表最终 14d 全部组件的冷构建统一为零警告。

### 3.3 Harness 客户端与启动诊断

Python 客户端支持上下文管理器、幂等关闭与重连，初始化一半失败时尽力清理已创建的资源；清理本身失败时保留最初异常并附加清理失败信息。HTTP 和 JSON-RPC 错误保留方法、状态、代码与 data，不会自动重放工具调用，避免把一次失败重试成重复的游戏操作。

缺少 `status.json` 的启动诊断不再简单地把等待超时当作“游戏未启动”。Linux 下核对实际 ONI 可执行文件和无歧义的 control 参数，再读取真实 HOME/XDG_CONFIG 以判断配置位置和伴随 Runtime 是否匹配。该诊断只报告证据，不擅自安装、重启或结束进程。

本轮相关验证包括 32 项 Runtime 启动器/诊断的离线测试（其中 10 项为新增）、50 项 Python 库测试用例、ruff、mypy 的 Python 3.10/3.15 目标、wheel/sdist 的 Twine 检查，以及 Windows/Linux 的 3.10/3.15 CI。平台矩阵是同一组用例的重复执行，静态检查和分发包门禁也不计入独立用例数量。`typing_extensions` 已显式声明，锁文件中 153 个版本保持不变。历史 13 个托管测试项目及 114 项 Python 检查与这些数字有覆盖关系，不将其相加成“独立测试总数”。

## 4. OniOnline：从入口到连接状态都可见

本轮补上主菜单房间浏览器的“创建房间”入口，以及不依赖世界模拟能力的 ChatOnly 建房路径。连接过程区分重试、等待、正在连接、重试耗尽和关闭，并显示次数、延时及错误。关闭星图时不再误触发整个管理器的销毁。

网络层接受发送，只说明传输层接收了请求，不能等同于对端业务已处理。相关状态和说明保持这个区别。模组目录也不再把所有扫描到的无效模组都当成阻断原因：同时未启用、未加载且未被明确请求的无效项仅记为诊断信息；当前已启用、已加载或被明确要求的无效项才阻断，源文件发生变化也会阻断。CycleTrim 仅在检测到已加载的 OniOnline 框架时注册联机玩法，并将 CycleTrim 自身声明为 Required 内容，同时提供对应 `.json` 声明；兼容检查要求精确版本和完整 SHA，不随包夹带另一份框架。

验证包含 4,818 个断言，覆盖实际 TCP 连接和 3 个独立客户端进程；120 项针对性子集中的 10 项为新增，不额外叠加到总数。CycleTrim SDK 的 10 项断言使用真实框架。测试工程的 Jlib 引用从 0.3.0 对齐到 0.3.10，使用隔离缓存中的源码包并核对实际 DLL 哈希；这不表示新的 NuGet 包已经发布。

最终候选的真实游戏主菜单中，房间浏览器、LAN 切换和建房路径均已打开。建房后实际显示绿色 `LAN / Connected`、1 名成员、`Host: You`、房间及邀请信息、复制按钮和聊天输入区。U60 的 Asteroids 控件保持禁用，显示 `This feature is not supported on this game version.`；点击没有关闭房间窗口。原生世界能力仍受游戏版本 744825 的适配白名单限制，U60 未放行这条路径；本轮 ChatOnly 单端建房不依赖该世界能力。建房后的异步刷新需要时间，切换前的 `Not connected` 截图没有被错误地记为建房失败。

上述验收仅证明**单个真实游戏实例中的 LAN 房主界面和能力提示**。第二个真实游戏加入、跨设备/互联网连接、实际聊天发送与对端送达、Start game 和共享模拟均未由这次 UI 检查证明。3 个进程的 TCP 测试也不替代两个完整 U60 游戏实例的验收。

## 5. onim、依赖与发布链

### 5.1 内置 ZIP 与事务式安装

onim 用进程内 ZIP 处理替换对外部 unzip/PowerShell 的依赖，安装使用临时阶段和失败回滚。对绝对路径、`..`、反斜线、设备名、控制字符、尾部点/空格、符号链接与特殊文件、文件/父目录冲突、大小写别名、重复 header 不一致等情况作明确处理；使用 `create_new` 防止静默覆盖。Unicode 名称、空目录和复制后的权限也有覆盖。

独立审查发现的父路径大小写别名缺口已补上。此前 86 项相关检查由 64 项单元测试、17 项真实 ZIP 的 CLI 用例和 5 项 setup 用例组成，并在 PATH 中没有 unzip 的情况下通过。约 215.5 秒的总耗时包括 Rust 锁等待，不是解压性能基准；没有据 Linux 的测试结果宣称 Windows/macOS 运行时已通过。

十六进制转换复用 Project Z 的 `zhex = 0.1.3`，采用固定 64 字节缓冲区，移除逐字节格式化；Cargo 清单和锁文件同步更新。Project Z 的外部仓库注册状态见第 8 节，源码引用已更新与注册图已闭环分别记录。

### 5.2 发布描述与封面契约

Rust 打包器选择一份主描述，优先英文，再回退中文或 YAML；每种语言按规范路径选择非空文件。没有再把两种语言拼成一个超长描述。实际限制按 UTF-8 字节计算；Rust Plan 保留 7,999 字节的保守上限，C# 上传器使用 8,000 字节检查，二者不混称为同一个门槛。

Jlib 的旧测试把预览图尺寸固定为 512，阻止了新的封面。测试与说明同步调整为：非空、符合本项目 Legacy 流程的 10 MiB 上限、PNG 签名与 IHDR 基本结构有效、边长为正且为正方形。它没有要求恰好为 1,254，也不声称仅检查头部等于完整解码或 Steam 接受。完整默认源码宿主检查共 2,391 个断言，其中 36 个预览图契约断言覆盖 5 个接受、31 个拒绝场景。宿主日志还读取了旧 0.2.0 nupkg 的元数据，因此这组结果不是新 0.3.10 NuGet 包的安装验收。此前 net48/netstandard2.1 冷构建记录的 52 项警告保留在日志中。
