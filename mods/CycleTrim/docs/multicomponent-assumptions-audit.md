# 多组分兼容性审查（2026-11-08）

本记录核对了用户提供的四模块清单，引用当前本地 `decompiled/` 和工作区源码。它是静态审查，不是游戏运行结果，也不证明清单穷尽了所有调用点。反编译目录当前有 4409 个 C# 文件；一次 Codegraph 查询未返回预期反编译符号，不能据此确认其索引覆盖或报告中的节点数量。当前未观察到 geg 索引进程，历史索引状态未验证。

## 关键结论

* 工作区的 `gpu_sim.rs` 只构造热扩散算子，并每步上传温度和质量、同步读取温度；多组分和压力算子尚未接入生产时间步。代码注释与此不一致。没有证据支持整局游戏达到 17.6 倍加速或 500 FPS。
* 当前模拟保存主元素和一个 `mixture` 覆盖，稠密气体通道在区域步开始时重新从这两项导入（`native/src/multicomponent_flux.rs`），输出又只投影前两项；三个及以上组分不能由此证明可持续保存。发布器目前最多实际填两项，压力、分压及体积占比为零。
* `world.rs` 的 `publish_to` 原样发布主元素的 `write.mass`，不是报告所述的全部组分质量之和。即使改为总质量，主元素加总质量也不能让消费、疾病、反应等调用自动正确；总质量冒充主元素质量还可能造成误消费。
* Jlib 中已有颜色、呼吸、建筑可用性、植物、导航和覆盖层补丁，`ModInfo.OniSim.cs` 有安装入口；这不等于它们均已接入当前运行的游戏或完成端到端验收。植物逻辑目前按质量计算，导航依赖的液体体积分数当前发布为零。

## 建议实现次序

1. 建立覆盖固、液、气的权威组分存储和按元素增删接口；每种物质质量、热量和病菌必须在输入、流动、挖掘、排挤和存读档中守恒。明确固体与可拾取物身份、占格和建筑掩埋的关系。
2. 确定压力与体积分数的物理定义并实现发布，再对呼吸、消费、植物、暴露和泳道做行为测试；读取得到的元素和实际扣除的元素必须一致。
3. 分别贯通管道全生命周期、渲染和覆盖层，测试跨格流动、建筑 I/O、不同相、保存和重启。
4. 将 GPU 求解接到实际生产时间步，测量上传、dispatch、同步与读回，比较真实游戏相同场景的帧时间及正确性；避免将孤立算子吞吐量当作游戏帧率。
