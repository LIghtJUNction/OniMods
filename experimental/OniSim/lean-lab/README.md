# OniSim：用 Lean 验证疾病扩散的几何遍历优化

已实现并实测：将疾病发射器的无障碍四邻接搜索改为按行枚举菱形区域。
Lean 4.19.0 实际检查了 34 个定理；65040 个 Rust 差分场景全部通过。
在 1024×1024 地图、8 个发射器、`max_depth=16` 的组件更新基准中，
原版耗时中位数为 170.651 微秒，改进版为 12.099 微秒；
8 对测量的加速比中位数为 **13.894 倍**。这是组件实测，游戏帧率尚未测量。

## 1. 原算法

原函数是 `native/src/disease_emitters.rs` 中的 `reachable_cells`。
它在每次搜索中执行以下操作：

1. 按整张填充地图的大小，申请并清零 `visited`。
2. 把中心放入先进先出的搜索队列。
3. 取出一个格子，检查深度、坐标和重复访问。
4. 接受格子后，把下、左、右、上四个邻居全部加入队列。
5. 把接受的格子放入返回向量，再由 `update` 更新这些格子的疾病状态。

这段代码不检查材料是否可通行。源码明确说明固体不阻挡此次搜索，实际函数也只
使用 `world.read.element.len()` 获取数组长度。因此，有效图是一个无障碍矩形。

设全图有 N 个格子，本次接受 K 个格子。原算法每次清零 N 个标记；完整搜索的
入队和出队次数均为 `1 + 4K`。其时间为 `O(N + K)`，临时内存为 `O(N + K)`。

## 2. 改进算法

四邻接网格中，两点的曼哈顿距离为：

    distance = abs(x - center_x) + abs(y - center_y)

原代码接受 `depth < max_depth`，所以有效半径为 `max_depth - 1`。
中心有效时，所有接受格子正好组成与有效矩形相交的菱形。

新模块 `native/src/diamond.rs` 每次返回一个连续行区间。调用方直接遍历区间，
不申请访问表、搜索队列或结果向量。

```text
sx = int(u16(start_x))
sy = int(u16(start_y))
upper_x = min(stride, 65536)
upper_y = min(padded_height, 65536)

如果 max_depth 为 0，或者转换后的中心不合法：返回空
radius = max_depth - 1

对于 y ∈ [max(1, sy-radius), min(upper_y, sy+radius+1))：
    reach = radius - abs(y-sy)
    first_x = max(1, sx-reach)
    end_x = min(upper_x, sx+reach+1)
    访问连续索引 [y*stride+first_x, y*stride+end_x)
```

新算法时间为 `O(K + 1)`，额外工作内存为 `O(1)`。若同一次模拟更新有多个
发射器，原来的反复全图清零项 `M*N` 被移除，工作量主要由实际受影响格子决定。

不受边界裁剪时，半径 r 的格子数为 `1 + 2*r*(r+1)`。例如 `max_depth=16`
表示半径 15，共 481 个格子；`max_depth=255` 表示半径 254，共 129541 个格子。
这些数值用于检查工作量，不代表游戏中的实际发射器分布。

曼哈顿距离和区间枚举是已有数学方法。本实验的新内容是把它们用于这段现有代码，
给出适用条件、可检查证明和真实源函数的差分实测；不主张新的数学发现。

## 3. 为什么改变格子顺序仍能得到相同状态

新算法按行访问。它的访问顺序可以与原来的逐层搜索不同。

`add_disease` 及其实际调用链只读取当前格子的疾病字段和只读疾病表，并只修改
当前格子的 `disease_idx`、`disease_count`、`disease_infestation`、
`disease_growth`。它不读邻格、不产生事件、不使用随机数，也不修改共享累加器。

因此，对不同格子 a 和 b 的更新可以交换：

    update_a(update_b(world)) = update_b(update_a(world))

相同格子集合、每格恰好一次，再加上上述局部更新性质，可以推出一次发射后的
最终状态相同。发射器之间的外层顺序保持不变；不能把这一结论推广为任意发射器
之间都能换序。

## 4. 必须保留的边界

| 条件 | 本次处理 |
| --- | --- |
| `max_depth=0` | 不访问任何格子。 |
| 输入是负数或超过 65535 | 先保留原来的 `as u16` 转换，再判断中心是否合法。 |
| 坐标 0 | 始终无效。 |
| 65535 加 1 后回到 0 | 0 会被拒绝，所以有效图不是首尾相连的环面。 |
| 最右、最上填充格子 | 保留原来的 `x < stride`、`y < padded_height`，不额外缩小范围。 |
| Region | 仍只限制发射器中心，不限制受影响格子。 |
| 多个发射器 | 仍按原顺序更新。 |
| 发射计时器 | 保留每次最多一次发射、减一次间隔、再加 dt 的原操作。 |
| 内存不足 | 新搜索不申请内存，消除了原搜索可能产生的申请失败。等价结论针对成功执行后的状态。 |
| 世界布局 | 仍依赖原有合法分配尺寸；本补丁不定义损坏的数组布局或整数溢出后的行为。 |

## 5. 证明与实现之间的对应关系

`proof/SimDiamond.lean` 使用 Lean 4.19.0 和内置 `Std`。证明分为：

- 合法四邻接路径的最少步数等于曼哈顿距离。
- 逐行区间覆盖恰好等于深度限制内的合法格子。
- 原始图搜索的有限参考模型与新遍历的格子集合相同。
- 新遍历没有重复，非法中心和零深度返回空。
- 合法列范围内，`y*stride+x` 不会把不同格子映射成同一索引。
- 对任意逐格局部更新，两个遍历得到相同最终状态。

Lean 的参考图搜索按深度枚举路径端点后去重，用于证明图搜索的数学语义。
它不是原 Rust 队列、分配器及其机器码的逐条形式化翻译。原 Rust 源函数与
新 Rust 源函数的对应关系由差分执行测试检查。源文件中的浮点疾病运算直接复用，
没有另写一套更容易通过测试的数学公式。

完整 SimDLL、官方闭源二进制、Rust 编译器及游戏运行兼容性不在本证明的结论中。

### 性能

全部正式性能数据已收集，原始样本没有删去较慢的一侧。
`harness/PROTOCOL.md` 在计时前固定了 60 个场景：256、512、1024 三种地图边长，

每场景有 8 对 AB/BA 交替测量，共 **960 个正式样本**；
每个正式样本是一批调用的总时间，再除以调用数，最短批次为 **18.022 毫秒**。
另保留 537 个预热样本和 236 个校准样本。
计时固定在 CPU 8，分配统计使用另一可执行文件，计时程序不启用分配计数。

glibc 2.39、Rust 1.99.1、LLVM 23.1.1。使用 Cargo release 默认优化，
没有 fast-math 或自定义 target CPU。容器固定了 CPU 亲和性，但未控制主机频率和

时间统一为 **微秒 / 整次 update**；K 是各发射器访问格数之和，重叠格按发射器
次数计入，并非覆盖区域的并集大小。

| max_depth | 半径 | K | 原版中位数 μs | 改进版中位数 μs | 配对加速比中位数 | 配对加速比最小–最大 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 0 | 8 | 97.560676 | 0.096428 | 1006.002× | 841.349–1104.563× |
| 4 | 3 | 200 | 100.834871 | 0.765102 | 130.690× | 115.768–141.715× |
| 16 | 15 | 3848 | 170.650729 | 12.098697 | 13.894× | 12.239–15.294× |
| 64 | 63 | 63224 | 1323.820825 | 224.388144 | 5.780× | 5.360–6.136× |
| 255 | 254 | 869271 | 20974.855000 | 2725.658500 | 7.626× | 7.384–7.952× |

“配对加速比中位数”先计算每对原版时间 / 改进版时间，再取 8 个比值的中位数。
它不等于两侧时间中位数相除。以深度 16 为例，后者为 14.105 倍，
按两侧耗时中位数计算的时间减少为 92.91%。原始数据和汇总文件同时保留两种统计，
本文标题数字采用配对比值。

深度 1 和 4 的大倍数来自原版每次都要清零整张地图大小的 `visited`。
深度 1 时，8 个发射器合计仅更新 8 个格子，改进版不再为它们清零约 842 万个
访问标记。这不代表一帧或整个模拟步会加速相同倍数。

| 公共地图尺寸 | K | 原版中位数 μs | 改进版中位数 μs | 配对加速比中位数 |
| --- | ---: | ---: | ---: | ---: |
| 256×256 | 3477 | 69.741813 | 10.606267 | 6.534× |
| 512×512 | 3727 | 93.244525 | 11.849353 | 7.791× |
| 1024×1024 | 3848 | 170.650729 | 12.098697 | 13.894× |

K 的变化来自发射器位置和地图边界裁剪。全部 60 个场景的配对加速比中位数都大于 1，
本次没有测得回退；15 个搜索场景中最低为 11.788 倍，45 个完整组件更新场景中
最低为 5.138 倍。预设的 36 个深度 1、4、16 场景全部超过 5% 时间减少门槛。
该结论只适用于已测场景，不据此保证其他负载的最小提升。

完整更新的计时负载使用稳定的“同病种、正数发射”路径。
每个测量批次从相同的种子世界复制开始，复制和最终状态消费放在计时之外；
函数执行、区域与计时器检查、所有发射器的真实疾病运算均在计时之内。
不同病种、负数发射及特殊浮点数在正确性测试中覆盖，没有作为这张表的计时负载。
搜索基准对每个索引使用相同的 `black_box` 和非线性校验，避免编译器用闭式求和
替换实际格子枚举。

### 形式化验证的主定理

完整证明在 `proof/SimDiamond.lean`，以下是其中实际已编译的主定理及证明体。
`r` 对应 `max_depth`，`Value` 表示一个格子的完整局部状态：

```lean
theorem bfs_checkedScan_same_updates {Value : Type}
    (b : Bounds) (c : Cell) (r : Nat) (update : Cell → Value → Value)
    (state : Cell → Value) :
    runUpdates update (bfs b c r) state =
      runUpdates update (checkedScan b c r) state := by
  exact runUpdates_same_set update _ _ (nodup_bfs b c r)
    (nodup_checkedScan b c r) (bfs_checkedScan_same_cells b c r) state
```

这里使用的同集合和无重复性质都在前面的定义上给出证明，没有把算法等价性
本身放进前提。34 个定理全部经过 Lean 内核检查，不含 `sorry`、`admit`、
`sorryAx` 或自造公理；使用标准逻辑公理不等于“完全不依赖公理”。

## 8. 复现

保留交付包的目录层次。先在新解压的副本里运行，复现实验会覆盖该副本的结果目录。
要求 Python 3.11+、C 链接器、Rust 1.99.1、Lean 4.19.0，以及 `rg`：

```bash
# 在交付包根目录，选择已安装的对应版本。
LEAN_BIN=/path/to/lean-4.19.0/bin/lean bash experimental/OniSim/lean-lab/proof/verify.sh
RUSTUP_TOOLCHAIN=1.99.1 python3 experimental/OniSim/lean-lab/harness/run.py all
```

若沿用源码项目的 RTK 约定，可在命令前加 `rtk bypass`。
Lean 仅依赖随安装提供的 `Std`；Rust 测试组件没有外部 crate。
`harness/README.md` 列出分阶段执行和 CPU 选择方法。
`all` 会重新核对原归档 SHA-256、编译、运行差分测试，再计时并统计分配。

交付前已在新的解压目录中再次通过 Lean 编译、两种 Rust 实验构建和 65040 个
差分场景；检查时没有带入原工作目录的 Lean 或 Rust 构建缓存。原归档上的补丁
检查也通过，记录见 `evidence/portable-check.json`。正式性能样本保留原实测数据，
这次解压复验没有重新运行或替换计时矩阵。

当前补丁可以对这个精确归档应用，组件证明与测试已经完成。
完整工程的 36 个已有整合错误仍需单独修复后，才能进入完整核心编译、游戏接管和
真实存档验证。本交付不包含可加载的完整 SimDLL 成品，也不把组件性能换算为 FPS。
